Everyone one repositoryone CODEOWNERS file one execution environment

One URL, and the environment is already correct

No laptop setup, no version drift, no "works on mine." The workspace ships from the repository, so every engineer who opens it gets the same editor, the same tooling and the same approved extensions.

redhat.ansible brings the Ansible language server and inline lint. redhat.vscode-openshift-connector brings cluster access. Nobody installs anything, and nobody can quietly drift.

The engineer writes the automation, and nothing else

A role from the shared collection, the two variables that make this change specific, and that is the whole file. The engineer is writing intent, not plumbing.

The same devfile.yaml that built this workspace pins the execution environment image that Ansible Automation Platform will run with later. That is what closes the gap between here and production.

ansible-lint reviews the change before a person has to

What it does: checks the playbook against a rule set for deprecated syntax, unqualified module names, tasks that report "changed" on every run, shell commands where a real module exists, and files left with unsafe permissions. It runs on save in the workspace and again on commit.

Why it matters here: it settles every style argument before review, so the reviewer spends their attention on whether the change is right rather than whether it is tidy. And it catches the class of defect that does not fail in test — the non-idempotent task that passes once, then quietly re-applies itself on every run afterward.

Because lint runs inside the same execution environment AAP uses, "passes here" genuinely means "parses there."

The pull request is where the machine checks happen

Four automated gates run before any human is asked for an opinion: syntax, lint at production profile, a molecule run that converges the role and then proves it is idempotent, and a check that the execution environment matches.

Merging is blocked, and not by policy or good intentions. The branch protection rule will not let it through.

Then the team that owns the directory approves it

This is the whole governance model, and it is one line of configuration. CODEOWNERS maps a directory to a team, and GitHub requires that team's approval on any change touching it.

Storage engineers own storage automation. Network owns network. Nobody waits on a central gatekeeper who does not know the domain, and nobody merges into somebody else's domain without them seeing it.

Check mode shows the change before it happens

The first job runs with --check. Ansible walks every task and reports what it would do without writing anything to the array.

Two changes predicted: create the volume, set the export policy. That output is the change record, produced before the change, and it is reviewable by someone who was not in the pull request.

Apply, and the result matches the prediction

Same job template, check mode off. Two changed, zero failed — exactly what check mode said.

It runs from main only, in the pinned execution environment, under the job template's own credentials. Approving the merge and being allowed to run it against production are two separate permissions, held by two separate systems.

The same path, whoever you are

Nothing above is specific to storage. Change the directory and the owning team and the identical loop runs for network, platforms and cloud.

Four teams keep their autonomy over their own domain. The organization keeps one review model, one tested content set, and one execution environment. That is the trade that usually has to be argued for, and here it falls out of the structure.
